# Deviation log

The Part-2 brief (item 2i) says: "Deviations from the submitted document should be documented and explained during the final demo." This log lists every way the build differs from the **submitted** documents: SRS v1.1, SAD v1.0 and Software Test Plan v1.0.

Each pull request that introduces a difference adds a row. The SRS v11 working draft referred to in code comments is the team's revised SRS, which supplies the detailed rules that SRS v1.1 leaves open.

**Status:**
- **Temporary**: closed by a later issue.
- **Permanent**: a deliberate decision, explained here.
- **Open**: still needs a team decision.

| ID | Submitted document says | The build does | Why | Status | Added by |
|---|---|---|---|---|---|
| D-05 | SRS 2.4 / SAD ADR-002: "file-based or lightweight relational database". | SQLite 3.50.4, vendored as source in `third_party/`. | It is within what was submitted; this records the choice. Vendoring makes the Windows and Linux builds identical. | Permanent (decision) | #1 |
| D-06 | HMS-NF-003, HMS-SR-005: sensitive data encrypted at rest. | Not encrypted. On Linux the store and lock file are created owner-only (mode 0600). | Encrypting the store needs an extra library (for example SQLCipher). Field encryption would break name and phone search. Disk encryption (BitLocker, LUKS) is a different protection and is not claimed to meet the requirement. | Open | #1 |
| D-07 | HMS-SR-005: restrict file access to the application. | On Windows the store and lock file are created with default permissions. | Windows owner-only ACLs are not implemented yet. | Temporary (#12) | #1 |
| D-08 | HMS-NF-002: ≥ 99 % availability, measured from uptime logs. | Crash safety instead: changes are all-or-nothing transactions, and failure-injection tests show nothing is half-saved. | Uptime can't be measured for a single-user desktop program, and no uptime log exists. | Permanent | #1 |
| D-10 | STP 6: Unity/CppUTest/Google Test, Valgrind, Jira/Trello. | doctest, AddressSanitizer + UBSan, GitHub Issues and GitHub Actions. | doctest is one header and builds identically on MSVC and GCC. Valgrind doesn't exist on Windows. The course uses GitHub. | Permanent | #1 |
| D-13 | — | An older data store is upgraded to the current schema on opening, one numbered migration at a time; a newer one is refused unchanged. | Each feature adds tables. | Permanent | #1 |
| D-01 | SRS 3.1, HMS-F-024: every role reaches its menu only after login. | Replaced by real staff login in #3: the role now comes from the stored account. | Login is issue #3. The service functions already take a `Session`, so login replaces only the code that creates it. | Closed by #3| #2 |
| D-02 | AC-HMS-F-002 (and issue #2 as first written): a matching phone number blocks a new UHID. | A shared phone number is allowed after staff review: the screen lists the existing patients with that number, and staff choose "same patient" (no new record) or "different person" (new UHID). A patient with the same name, date of birth and gender is a *strong* match and needs a reason code. The submitted behaviour is one setting: `PatientPolicy::phoneMatchAllowsNewPatient = false`. | The submitted requirement contradicts its own acceptance criterion: the requirement text says "warn and require explicit confirmation", the criterion says "block". In India one mobile number is commonly shared by a family, and blocking would push staff to invent numbers. | Permanent (team decision) | #2 |
| D-03 | HMS-F-001: "age/DOB" (which one is stored is not stated). | The date of birth is stored. When it isn't known, the age is accepted and stored as an estimated date of birth (1 January of the birth year), flagged and shown as "estimated". | A stored age goes stale every year. This keeps the submitted "age" option. | Permanent | #2 |
| D-04 | HMS-F-001: "contact details" (undefined). | One optional Indian mobile number, accepted as 10 digits or with 0, 91 or +91 in front, stored as the 10 digits. A patient may have no phone. | A definition was needed; it follows the team's v11 SRS 1.4. | Permanent | #2 |
| D-11 | SAD 4.4.1: `registerPatient(name, age/DOB, gender, contact, address) → UHID`, error "duplicate phone". | `registerPatient(session, draft, decision)` returns *Registered* or *NeedsDecision* (the possible duplicates); `useExistingPatient` records a "same patient" decision. | The duplicate review needs a two-step handshake, and the role check needs the session. | Permanent | #2 |
| D-12 | — | Search shows at most 50 rows, in name order, and reports the total. | Readability on a large store. | Permanent | #2 |
| D-14 | SAD class diagram: `Patient(patientId, name, age, gender, phone, address)`. | Table `patient(uhid, full_name, normalised_name, date_of_birth, dob_estimated, gender, address, phone)`, plus `audit_entry`, `duplicate_review` and `duplicate_review_candidate`. | The date of birth replaces age (D-03). The duplicate-review tables store each decision with the patients that were reviewed (HMS-F-002). | Permanent | #2 |
| D-15 | HMS-F-023: Administrator creates and manages staff accounts. | The first Administrator is created at first start-up, because no account exists to log in with. After that the Admin menu can create accounts only. There is no reset, unlock or deactivate screen yet. | The system needs a first account, and account management is planned for Sprint 2. | Temporary | #3 |
| D-16 | HMS-SR-003: account locks after repeated failures, with a cooldown. | The account locks after 5 failed attempts and stays locked. | D-17 | HMS-SR-001, HMS-SR-003: login failures, lockouts and denials are audited. | Authentication does not write audit entries yet. (Patient-module denials are audited by #2.) | The audit module arrived with #2 and was not wired into login in Sprint 1. | Temporary | #3 |

Lab technician and pharmacist roles are not in the table yet. | Those roles have no screens in Sprint 1. | Temporary | #3 |
